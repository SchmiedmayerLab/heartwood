Platform API and Access Requirements¶

These are the APIs, access and deployment controls a platform team such as Terra or Seven Bridges provides to integrate Heartwood. The Platform Contract defines the message semantics, versioning and conformance checks behind each request.

Select the Integration Scope¶

Hosting, isolated workers, inference and research services are independent capabilities; select only what the integration needs and start with a synthetic project.

Capability Requested from the platform Heartwood status
Run the application A release artifact, durable storage and an authenticated researcher route Current; interfaces depend on the platform adapter
Isolate complete workers A Docker engine and sandbox gateway under operator control, protected state, selected read-only inputs, bounded writable storage and enforced egress Current for the OpenShell Docker reference adapter; qualified only against the qualification-only gateway build
Use approved inference Authorized model discovery and an inference endpoint with streaming and native tool calls Current through built-in and configured routes; connection-manifest startup unavailable
Inspect research metadata Authorized project, dataset, file and workflow descriptions Draft profile and offline checks; no built-in connector
Execute research workflows Native submission, status, results and cancellation with independent authorization Draft profile; the trusted Python outside operation interface requires a platform-specific adapter
Estimate work and inspect budgets Platform-owned estimates, observed spend and allocation constraints Draft schemas only

The service requests below describe an integration target; no Terra workflow or Seven Bridges connector is installed. The Terra image supports the documented terminal and notebook paths.

Hosting and Researcher Access¶

Provide one authorized research directory and persistent canonical state on storage with native advisory locks that preserves the project UUID across restart and restore; an object-store mount is not sufficient because it exposes files. For a managed project, bind state outside the research directory with an operator-owned deployment manifest and keep it inaccessible to workers. The manifest is read only by heartwood gateway serve --deployment, heartwood project migrate and heartwood project recover-migration; qualify each interface against the gateway it binds.

Provide, without secret values:

  • the artifact digest, architecture and execution shape;
  • the research directory, state location and the operator responsible for their binding;
  • the authenticated public origin, exact base path, proxy source ranges and TLS termination;
  • the secret-manager reference or protected descriptor source for the gateway capability;
  • gateway lifecycle, session expiry, backup and restoration arrangements; and
  • the available interfaces and the synthetic environment used to qualify them.

The proxy authenticates and authorizes the researcher, strips client-supplied forwarding and identity headers, supports unbuffered streaming and WebSocket upgrades, and prevents direct access to the gateway. Use one gateway per researcher and project, and separate authenticated origins for mutually untrusted projects. Heartwood does not verify OpenID Connect identities or exchange platform tokens. The Gateway API reference and the generated gateway.openapi.json define every route.

Inference Access¶

For a compatible inference service, provide the API base URL, the authenticated model-list endpoint and the approved model identifiers. The model list returns only the caller's authorized models. The minimum profile is Chat Completions with streaming and native tool calls; declare Responses support separately. State context and output limits, tool support, rate limits, quota behavior, permitted data classes, retention terms and region restrictions where known; missing declarations stay unknown. Declare each connection's data handling: the destination class of the complete route, including any gateway and its ultimate providers, and the authority that governs retention. A deployment that must keep content within a boundary lists the permitted destinations in its policy's allowed_data_destinations; a profile without external egress lists only same-compute.

For isolated workers, the outside inference transport holds the real credential and gives the worker only a placeholder. The reference adapter uses the OpenShell inference transport; an institutional gateway can remain the provider endpoint behind it. Enforce model and tenant restrictions at the provider or an authorized inference gateway, because a hostname allowlist does not constrain which account, model or request a compromised worker sends there. State whether the credential authorizes one model or an approved set, and demonstrate revocation separately from rotation, including existing connections. A Heartwood-managed local model server is not reachable from an isolated worker; local compute for a worker needs a separately authenticated outside route.

Research Service APIs and Permissions¶

Select each capability individually; inspection does not imply permission to execute, export or change membership. Credentials belong to the trusted outside adapter, and the platform checks the caller's permission on every request. Never give raw platform credentials or unrestricted API tools to a worker.

Capability Required API behavior Minimum access to request
Project discovery Resolve an authorized project and its stable identifier Read selected project metadata
Dataset and file discovery Return identifiers, metadata, versions or checksums, and access restrictions Read metadata for selected resources
Input access Resolve authorized content or scoped retrieval references Read only the selected data
Workflow discovery Retrieve the immutable workflow or app revision, input schema and resources Read approved workflow definitions
Submission Submit the exact reviewed native request and return an operation identifier Execute only in the selected project and billing context
Monitoring Read status, outputs and permitted logs by operation identifier Observe the authorized operation
Cancellation Request cancellation and observe the terminal outcome Cancel the authorized operation only
Output publication Write reviewed outputs to an authorized destination Destination-scoped write or export permission
Budget observation Return timestamped allocation and spending, including unknown or delayed values Read the relevant allocation; no billing-administrator role

State which APIs accept idempotency keys or support lookup after a lost response; a native POST is not assumed safe to retry. Cancellation acknowledgement does not prove that work or charges stopped, and data retrieval, logging and export can incur cost under read-only permissions. An MCP service for these capabilities follows the service discovery profile.

Terra¶

These requirements apply to the Google Cloud Terra workspace integration; confirm the deployment and cloud first. Terra workflows use WDL and Cromwell; provide the approved workflow revision and configured inputs. See Terra workflow execution.

Request a synthetic workspace, an authorized principal and a declared permission set. Request Reader for inspection, and Writer with Can-compute for workflow or interactive-compute launch. Writer also permits changes to workspace tables and method configurations; use a dedicated integration workspace when that authority is unacceptable. Owner and sharing permissions are not required. Workspace charges use its Terra billing project, and some read or copy operations incur transfer costs. See Terra workspace access controls.

The Terra API specification defines these routes relative to /api/workspaces/{workspaceNamespace}/{workspaceName}:

Operation Native method and path Requested access
Inspect data-table types GET /entities Selected workspace metadata
Inspect workflow configurations GET /methodconfigs Approved configuration metadata
Inspect submission history GET /submissions Authorized workflow history
Submit the reviewed configuration POST /submissions Writer with Can-compute
Monitor the submission GET /submissions/{submissionId} Authorized submission state
Read workflow execution metadata GET /submissions/{submissionId}/workflows/{workflowId} Authorized metadata; outputs may need storage access
Request abort DELETE /submissions/{submissionId} Abort permission; observe terminal status afterward

Use the native specification for request bodies and validation. Confirm bucket and object access and controlled-data entitlements separately from workspace metadata access. Include the Terra Data Repository API only when the selected datasets require it. Use a least-privilege user or service identity following Terra's service-account guidance, and never mount a researcher's cloud credential directory into a worker.

Seven Bridges¶

Confirm the deployment and regional API base: the public Platform documents https://api.sbgenomics.com/v2 (AWS US) and https://eu-api.sbgenomics.com/v2 (AWS EU). The API authenticates with X-SBG-Auth-Token; keep the token in the outside adapter. See the Seven Bridges API overview.

Request a synthetic project, its identifier and an approved app revision. Use the native project, file and app APIs for discovery; file identifiers select inputs. The task lifecycle is:

Operation Native API relative to /v2 Reference
Create a draft task POST /tasks Create a draft task
Start the reviewed task POST /tasks/{task_id}/actions/run API task workflow
Read status and outputs GET /tasks/{task_id} Get task details
Request cancellation POST /tasks/{task_id}/actions/abort Abort a task

Read covers names, metadata and workflows; Copy covers content access and downloads; Execute covers running and aborting tasks; Write covers changes to files and workflows. Admin, membership and funding-source permissions are not required. See Seven Bridges project permissions. These permissions apply per project, so use a dedicated project when the required authority must be narrower than a platform role. The platform keeps the project billing binding, and a download URL or copied file is not approval to export controlled data.

Audit and Records Access¶

Provide the signer endpoint, its authentication mechanism, the approved deployment identifier, public verification keys with key versions, and the retention policy. The signer implements POST /v1/checkpoints/sign as described in Audit and Records; it is an outside service, not a gateway route.

For managed evidence, also provide the records service origin, versioning and Object Lock retention, authorized publishers and readers, and the restore procedure, with these principals:

Principal Authority Boundary
Gateway Stage candidate audit and experiment records, read retained history, request signing for its scope No checkpoint publication, signing key or policy administration
Signing service Authorize the fixed scope, read candidates and retained history, sign and conditionally publish checkpoints Private key stays in the service or its KMS or HSM; no retention bypass or deletion
Independent verifier Read retained versions, signatures and retention metadata No write, signing or key administration
Worker None No credentials for or network route to these services

Records Permissions and Retention maps these roles to S3 actions. A signing endpoint that returns a valid signature without retaining the checkpoint first does not satisfy managed evidence. Define how loss of signing, retention or telemetry is detected and which work stops.

Worker and Sensitive-Data Controls¶

The complete worker, including its model client, tools and subprocesses, belongs inside the externally enforced boundary; the gateway keeps policy, approvals and canonical records outside it. Request mandatory filesystem and process controls, resource limits and default-deny networking with exact approved routes. Qualification must cover private and metadata addresses, alternate routes, redirects, peer workers, management endpoints and process inheritance on the selected infrastructure. No Docker socket, infrastructure credential, research-directory mount or state mount belongs in the worker. The reference adapter needs an operator-controlled Docker engine; it does not hand Docker administration to the researcher or agent.

Gateway Behavior Behind Native Qualification¶

Heartwood does not distribute a production sandbox gateway. Native qualification runs against a gateway built only for qualification from the upstream OpenShell revision and the two patches recorded in images/worker/candidate/gateway.json. Its revocation and cleanup evidence depends on two behaviors of that build that the unmodified upstream release at the same revision lacks:

  • The Docker driver rejects deletion of a sandbox whose provisioning has not settled, instead of abandoning the provisioning task; without it, a container request already sent to Docker can produce a worker after the gateway reported the sandbox deleted and Heartwood recorded its absence. The driver reports it as capability openshell.compute.delete-awaits-provisioning.
  • An explicit delete of a sandbox already marked as deleting calls the driver again; without it, a failed deletion stays marked as deleting, later requests are acknowledged without cleanup, and revocation times out without evidence of absence. The gateway reports it as capability openshell.compute.delete-retries-deleting on its compute driver.

A deployment's gateway must provide both behaviors before qualification results for revocation or cleanup apply to it. Before it serves, launches a worker or reconciles a retained attempt, Heartwood reads the registered gateway's info through the GetGatewayInfo API. It requires exactly one compute driver, implemented as openshell/docker, whose negotiated capabilities include both, and otherwise stops with HW-WORKER-001 before any sandbox, volume or deletion request. The gateway version does not satisfy the check. The decision is retained, with the reported version, driver and capabilities, in each worker attempt's evidence: an accepted gateway in the runtime binding and revocation evidence, a refused launch in the evidence that recorded the attempt as not created. The check relies on the gateway's own report: a gateway that reports a capability it does not implement passes, and Heartwood does not test the deletion behavior of the registered gateway. Both capability names come from the qualification build's patches; no upstream release reports them, so an unmodified upstream gateway is refused. The qualification build also reports 0.1.8+heartwood.3, a local version that no upstream release uses, and the gateway_build entry of the qualification evidence records that version, its source revision and binary digests. Compare the deployed gateway with that record, or repeat native qualification against it and retain the evidence.

Sensitive Data¶

Sensitive-data use requires institution-approved data eligibility, provider agreements, residency, retention, monitoring and output-release controls for the exact deployment. Heartwood provides selected-input staging and read-only mounts, not quarantine or steward-approved release. Managed evidence in required mode blocks a reviewed action while signing or retained-history verification is unavailable; buffered mode lets ordinary work continue with a visible gap, but outside operations and result releases still wait for retained evidence. A successful synthetic sandbox run is not sensitive-data approval.

Information to Return¶

Item Requested information
Scope Hosting, isolation, inference, metadata, workflow execution, output publication and budget capabilities, each selected independently
Environment Deployment, cloud, region, synthetic project identifier and technical contact
Identity Principal type, audience and scopes, project permissions, token lifetime, secret reference and revocation mechanism
APIs Base URLs, specification versions, selected operations, request limits, pagination, retry and error semantics
Inference Model identifiers and protocols, permitted model set, data eligibility, declared data handling per connection, permitted data destinations, quota and retention terms
Storage Research and state locations, project identity binding, locking, backup and restore, input and output controls
Network Proxy origin and base path, gateway access restrictions, approved egress and its enforcement
Compute Worker architecture, isolation mechanism, sandbox gateway version, image policy and resource limits
Operations Workflow or app revisions, billing binding, status and cancellation behavior, lost-response reconciliation
Records Signer endpoint and identity, verification keys, retention destination and policy, publisher and verifier permissions, restore procedure
Evidence Synthetic test procedure, audit correlation, revocation checks, known limitations and the institutional approval owner

Send identifiers and secret-manager references through the integration documentation and credentials through the approved secret channel. Never include real research data or credentials in examples, tickets or qualification artifacts.

Contract Bundle and Acceptance¶

Export the contract bundle and distribute the complete directory with these requirements, the Platform Contract, the Gateway API reference and the exact source revision or release digest. The bundle supports integration and access review; it does not assert that draft services are deployed.

Check captured model and service responses with the offline conformance checks, then qualify the artifact in the synthetic environment. For each selected capability, return an authorized control and its rejected alternative; a failed request alone can indicate a broken service rather than effective policy.

Capability Authorized control Rejected or interrupted control
Gateway access The owning researcher reaches the declared route and reconnects to the event stream Another principal, an invalid capability, a wrong origin or a direct upstream connection is refused
Inference The approved model and identity complete a bounded synthetic tool call A disallowed model or tenant, direct credential access and a revoked worker route fail
Data access A selected synthetic input is readable through its staging route Unselected resources, writes to read-only inputs and unauthorized export fail
Workflow execution The exact reviewed request yields a correlated native operation Changed inputs or project, expired approval and conflicting replay fail; a lost reply reconciles without resubmission
Retained evidence An authorized checkpoint is readable and verifies after restore Wrong-scope signing, unauthorized publication, replacement and deletion fail; a required-mode outage prevents dispatch
Worker lifecycle The outside controller admits and then revokes the exact attempt The worker cannot reach protected state or management authority; uncertain deletion does not release ownership

For capabilities without a Heartwood runtime integration, platform-side evidence establishes only the native service behavior. Record the result against the deployment following Validate a Platform.
